# Код к статье

## Что здесь

`kotlin/` — четыре класса из приложения `app_hand_track`, которые реализуют описанный в статье метод:

| Файл | Роль | Раздел статьи |
|---|---|---|
| `OrientationEkf.kt` | кватернионный EKF и гейт акселерометра | IV-B |
| `ZuptDetector.kt` | скользящая дисперсия и порог по угловой скорости | IV-C |
| `TrajectoryIntegrator.kt` | интегрирование трапециями и обнуление скорости | III, IV-C |
| `RestSegmentCorrection.kt` | оценка и вычитание постоянной ошибки между остановками | IV-C |

Это не отдельный проект, а выдержки из модуля `:core` приложения. Чтобы они собирались, нужны ещё `Vec3`, `Mat3`, `Quaternion` и `StreamingTracker` из того же модуля. Полный исходный код — в проекте приложения.

## Самодостаточный пример

`../experiments/rest_correction_demo.py` не зависит от Android и не требует библиотек. Он показывает принцип коррекции на одномерном движении:

```bash
python3 ../experiments/rest_correction_demo.py
```

Ожидаемый вывод:

```
Истинное смещение за участок:      0,000 м
Оценка постоянной ошибки:          0,0400 м/с^2 (истина 0,0400)
Скорость в конце без коррекции:    0,2400 м/с
Ошибка положения без коррекции:    0,7200 м
Ошибка положения после коррекции:  0,0006 м
```

Это не те числа, что в статье (там 60-секундная 3D-запись), а минимальная иллюстрация: постоянная ошибка 0,04 м/с² даёт 0,72 м ухода, коррекция возвращает ошибку к уровню 10⁻⁴ м.

## Как перенести в свой проект

1. Возьмите `RestSegmentCorrection.kt` и `ZuptDetector.kt`.
2. Убедитесь, что есть типы `Vec3` и `Quaternion` с операциями `+`, `-`, `*`, `norm`.
3. Передавайте в корректор времена, линейные ускорения, флаги остановок, позиции и скорости.
4. Применяйте коррекцию только к участкам, ограниченным двумя остановками длиной не меньше 20 отсчётов.
5. Сохраняйте `segments` в метаданные сессии: по ним видно, сколько участков исправлено и какая ошибка вычтена.
